# ADR 0001: границы архитектуры бота

## Статус

Принято.

## Контекст

Бот решает один процесс: оформление и сопровождение разового гостевого пропуска.
Для хакатона важно, чтобы проект был понятным, быстро разворачивался и при этом
не выглядел как один большой файл, где смешаны MAX API, SQL и сценарии диалога.

## Решение

Оставляем один Go-сервис и один исполняемый пакет `cmd/maxbot`, но держим внутри
четкие границы:

- `max_api.go` отвечает только за транспорт MAX API;
- `polling.go` принимает события, группирует их по пользователям и ведет диалог;
- `domain.go` хранит правила статусов, проходов, просрочек, уведомлений и аудита;
- `storage.go` содержит схему PostgreSQL и базовые операции с данными;
- `request_views.go`, `admin.go`, `tech_admin.go` собирают интерфейс конкретных ролей;
- `extra_fields.go` отвечает за конструктор дополнительных полей формы;
- `observability.go` держит healthcheck, Prometheus-метрики и SQL-адаптеры;
- `util.go` содержит маленькие функции форматирования и валидации.

Такой вариант дает аккуратную архитектуру без лишней сложности. Для следующего
этапа эти же границы можно перенести в `internal/domain`, `internal/storage`,
`internal/maxapi` и `internal/bot`.

## Последствия

- Код проще читать на защите: у каждого файла есть своя зона ответственности.
- Деплой остается простым: один бинарник, PostgreSQL и мониторинг.
- Тесты могут проверять сценарии целиком через Say/Click/Expect, не поднимая MAX.
- При росте проекта появится понятная точка для выделения пакетов и миграций БД.
